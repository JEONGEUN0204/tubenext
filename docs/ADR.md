# Architecture Decision Records

## 철학
MVP 속도 최우선. 외부 의존성 최소화. 작동하는 최소 구현을 선택한다. "나중에 확장 가능하게"를 이유로 추상화를 추가하지 않는다.

---

### ADR-001: Next.js 15 App Router 단일 앱
**결정**: 프론트엔드와 API를 Next.js 앱 하나로 합친다. 별도 백엔드 서버를 두지 않는다.
**이유**: API 키를 서버에서만 다뤄야 하는데, 라우트 핸들러 하나면 충분하다. 배포 단위가 하나다.
**트레이드오프**: 분석 파이프라인이 한 요청 안에서 끝나야 해서 응답이 10~30초까지 걸릴 수 있다. 백그라운드 잡 큐는 MVP 범위 밖.

### ADR-002: YouTube API는 SDK 없이 fetch로 직접 호출
**결정**: `googleapis` 패키지를 쓰지 않고 `fetch`로 REST 엔드포인트를 직접 호출한다.
**이유**: 쓰는 엔드포인트가 `channels.list`, `playlistItems.list`, `videos.list`, `search.list` 4개뿐이다. `googleapis`는 수십 MB짜리 의존성이다.
**트레이드오프**: 응답 타입을 직접 좁혀 써야 한다. → `services/youtube.ts`에서 도메인 타입으로 정규화해 해결한다.

### ADR-003: 인증은 API 키만, OAuth 없음
**결정**: YouTube Data API 키로 공개 데이터만 읽는다. 채널 소유자 인증(OAuth)을 하지 않는다.
**이유**: OAuth 동의 화면·리프레시 토큰·콜백 라우트가 MVP에서 가장 큰 구현 비용이다. 공개 데이터만으로 "무슨 콘텐츠를 하는 채널인가"와 "뭐가 터지고 있나"는 충분히 답할 수 있다.
**트레이드오프**: 시청 지속 시간, 노출 클릭률, 시청자 인구통계 같은 소유자 전용 지표는 쓸 수 없다.

### ADR-004: 채널 프로필 추출과 추천 생성에 Claude 구조화 출력 사용
**결정**: `client.messages.parse()` + `zodOutputFormat(스키마)`로 JSON을 받는다. 모델은 `claude-opus-5`.
**이유**: 한국어 제목에서 니치·포맷·검색 키워드를 뽑는 일은 형태소 분석기나 키워드 빈도 계산보다 LLM이 압도적으로 낫다. 구조화 출력을 쓰면 응답 파싱 실패와 프롬프트 땜질이 사라진다.
**트레이드오프**: 분석 1회당 Claude 호출 2회 → 비용과 지연이 발생한다. 대신 정규식 파싱과 한국어 토크나이저를 들이지 않는다.

### ADR-005: 바이럴 지표는 "구독자 대비 조회수 배율"
**결정**: 순위는 `조회수 / 업로더 구독자 수`(아웃라이어 배율)로 매기고, 일 평균 조회수를 보조 지표로 표시한다. 구독자 수가 0이거나 조회수가 최소 기준 미만인 영상은 제외한다.
**이유**: 절대 조회수로 정렬하면 대형 채널만 나와서 참고가 안 된다. 배율은 "채널 규모 대비 얼마나 터졌나"를 보여주므로 소형 채널의 재현 가능한 히트를 찾아낸다.
**트레이드오프**: 구독자 수가 아주 적은 채널에서 배율이 과장된다. → 최소 조회수 임계값으로 걸러낸다.

### ADR-006: 저장소 없음, 캐시 없음
**결정**: DB를 두지 않고 매 요청마다 계산한다. 결과 캐싱도 하지 않는다.
**이유**: 저장할 사용자도, 비교할 과거 데이터도 MVP엔 없다. 스키마·마이그레이션·커넥션 관리가 전부 사라진다.
**트레이드오프**: 같은 채널을 다시 분석하면 API 할당량을 또 쓴다. 하루 약 30회 분석 예산 안에서는 문제되지 않는다.
